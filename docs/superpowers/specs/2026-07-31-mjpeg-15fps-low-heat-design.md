# OV5640 15 FPS MJPEG 低温预览设计

## 目标

在保留原生 128×128 JPEG 单张采集能力的同时，为网页增加约 15 FPS 的 MJPEG 实时预览，并通过降低 OV5640 输入时钟减少摄像头持续工作负载。优先级依次为稳定、较低温升、低预览延迟和画面流畅度。

## 当前基线

- 已编码并构建：OV5640 使用 128×128 JPEG、双帧缓冲和 `CAMERA_GRAB_LATEST`。
- 已上板验证：`/capture` 可以显示图像，`capture_failures` 为 0，修复 JPEG 缓冲区后不再出现 `cam_hal: FB-OVF`。
- 已测量：现有快照接口连续请求平均约 90 ms，约等于每秒 11 张；网页使用 200 ms 定时器，显示上限为 5 FPS。
- 尚未测量：OV5640 的实际输出 FPS 和摄像头表面温度。

## 选定方案

### 摄像头

摄像头配置改为：

```c
.xclk_freq_hz = 16000000
.pixel_format = PIXFORMAT_JPEG
.frame_size = FRAMESIZE_128X128
.fb_count = 2
.grab_mode = CAMERA_GRAB_LATEST
```

根据当前 OV5640 驱动的 PLL 和 128×128 时序配置，16 MHz XCLK 对应的理论帧率约为 15.8 FPS。该数值是配置推算值，最终以设备测量为准。

继续使用双缓冲，保证流处理取得最新帧并降低预览延迟。不改为单缓冲，因为单缓冲会增加等待 VSYNC 的延迟和帧率波动。

### HTTP 服务

使用两个独立的 ESP-IDF HTTP 服务：

- 端口 80：网页、`GET /capture`、`GET /api/status`
- 端口 81：`GET /stream`

两个服务必须配置不同的服务端口和控制端口。MJPEG 请求是长时间运行的处理函数，独立服务可以避免它阻塞网页、状态和单张采集请求。

不新增自定义摄像头采集任务。摄像头驱动和两个 HTTP 服务已经分别运行在 FreeRTOS 任务中，当前需求不需要额外队列或任务。

## MJPEG 数据流

`GET /stream` 返回：

```text
Content-Type: multipart/x-mixed-replace;boundary=<boundary>
```

连接建立后重复发送：

```text
--<boundary>
Content-Type: image/jpeg
Content-Length: <bytes>

<JPEG data>
```

每一帧按以下顺序处理：

1. 通过现有摄像头互斥接口取得最新帧。
2. 发送 MJPEG 边界、帧头和原生 JPEG 数据。
3. 无论发送成功或失败，都归还摄像头帧缓冲。
4. 按固定时间基准等待到下一帧周期。

目标周期为 67 ms，理论显示上限约 14.9 FPS。限速采用按周期补足剩余时间的方式；如果一次获取和发送已经超过 67 ms，则不再额外等待，避免发送耗时与固定延时叠加。

流服务显式设置 `max_open_sockets = 1` 并关闭 LRU 清理，只允许一个 MJPEG 会话。ESP-IDF 的同步长连接处理函数占用流服务任务，因此额外连接由 socket 容量限制等待或拒绝，而不是由 URI handler 返回应用层 503；关闭 LRU 可以防止新连接主动清除正在播放的流。

## 网页行为

网页使用原生尺寸显示：

```html
<img src="http://192.168.4.1:81/stream">
```

删除现有的 200 ms `fetch`、Blob 和 Object URL 自动刷新逻辑。保留：

- 原生 128×128 显示
- 暂停/恢复预览按钮
- 单张采集按钮

暂停时清除流图像的 `src`，使浏览器中止 MJPEG 连接；恢复时使用带时间戳的流 URL 重新连接。`/capture` 保持独立，用于手动抓拍和后续数据集保存。

## 并发和缓冲区所有权

- `/stream` 和 `/capture` 统一通过 CAMERA 组件的互斥接口取得帧。
- 帧数据发送完成前不得归还帧缓冲，避免驱动覆盖仍在发送的数据。
- 流每发送一帧后先归还缓冲，再等待下一周期，为 `/capture` 留出取得互斥锁的机会。
- 状态计数器由两个 HTTP 服务任务访问，读取和更新使用短临界区保护；网络发送过程不得处于临界区内。

## 状态与错误处理

`GET /api/status` 保留现有字段并增加：

- `camera_xclk_hz`
- `stream_target_fps`
- `stream_client_connected`
- `stream_frame_count`
- `stream_failures`
- `stream_fps`

行为约束：

- 摄像头取帧失败时增加失败计数，并短暂让出 CPU；连续失败时结束当前流连接，允许浏览器重连。
- JPEG 分块发送失败通常表示客户端断开；立即归还帧缓冲、清除客户端状态并结束处理函数。
- 所有退出路径都必须清除“流客户端已连接”状态。
- 正常发送不逐帧打印日志，只记录服务启动、连接、断开和错误，避免串口影响运行。

## 测试与验收

### 主机测试

- 先增加失败测试，再修改实现。
- 验证摄像头 XCLK 为 16 MHz，仍为 128×128 JPEG 双缓冲。
- 验证网页使用 `/stream`，不再包含 200 ms 快照轮询和 Blob URL。
- 验证 MJPEG Content-Type、边界、帧头和 JPEG 数据发送顺序。
- 验证成功、取帧失败、发送失败和客户端断开路径都正确归还帧缓冲并清除连接状态。
- 验证流服务只允许一个 socket，关闭 LRU，并使用独立服务端口和控制端口。
- 验证 `/capture` 和原有状态字段仍然可用。

### 构建验证

- 运行全部主机单元测试。
- 使用项目当前 ESP-IDF 5.5.4 环境完成固件构建。
- 报告固件大小和应用分区余量，不把构建成功描述成硬件验证成功。

### 设备验收

- 串口没有 `cam_hal: FB-OVF`。
- `stream_fps` 在正常光照下稳定在 14～16 FPS。
- 预览期间调用 `/capture` 仍能得到有效 JPEG。
- 连续运行至少 10 分钟，无重启、无持续采集失败。
- 在相同环境和运行时长下比较 24 MHz 与 16 MHz 的摄像头温度。没有测温工具时只记录主观温升，不宣称已经量化降温。

## 非目标

- 本次不加入录像、SD 卡存储、鉴权、OTA 或多客户端视频分发。
- 本次不修改 128×128 分辨率、JPEG 质量和 8192 字节 JPEG 帧缓冲配置。
- 本次不删除 `/capture`，也不改动后续模型训练或推理路径。
