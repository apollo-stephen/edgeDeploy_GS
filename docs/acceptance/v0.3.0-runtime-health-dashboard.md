# v0.3.0 Runtime Health Dashboard Acceptance

## Status

**Accepted for the scoped v0.3.0 functional release on 2026-08-10.**

This record covers the optional runtime-health task, its strict HTTP control
API and lease mechanism, and the responsive dashboard metrics and charts. The
real-board evidence covers default-off startup, manual enable, live metrics,
phone chart presentation, manual disable, continued inference, and absence of
panic/watchdog/reboot during the focused run.

This acceptance does not claim a 30-minute or multi-hour soak, injected
degradation/recovery, P99/WCET/deadline data, or watchdog-based recovery.
Lease expiry and rapid/idempotent lifecycle interaction are covered by host
tests rather than a separate final-board observation.

### Disable and continued inference

The user switched monitoring off and confirmed that the charts collapsed and
the disabled state behaved normally, including the copy:

`健康任务未开启，网页不请求健康数据，不占用监控任务栈。`

attempt encountered `Camera is busy` while the MJPEG client was active; the
next attempts succeeded without intervention. This is the existing bounded
CAMERA-mutex contention behavior, not a health-monitor failure.

## Accepted software contract

- The health task is not started by `app_main()`.
- The dashboard switch dynamically starts and stops `runtime_health`.
- `POST /api/health/control` accepts only one boolean `enabled` member.
- Enabled `GET /api/health` requests renew the 10-second client lease.
- The monitor task samples every second, wakes for explicit stop, and exits
  itself rather than being deleted by its caller.
- The inference pipeline remains active regardless of monitor state.
- Browser history is volatile, sequence-deduplicated, and bounded to 60
  samples.
- `monitor_uptime_ms` explicitly denotes health-monitor session uptime; the
  inference event timestamps remain boot-relative.
- Charts expose rounded scale values, current values, and the actual retained
  monitor time span without adding a third-party library or board history.
